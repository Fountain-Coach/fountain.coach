# Fountain Press Bookshelf: deterministic published-content frontend

**Decision pinned by the writer, 16 November 2026.** This is a source-owned frontend maintenance contract for the *existing* Fountain Press/Linotype Reader. The analogy is a conventional CMS: publication records are the data model, a reusable HTML/CSS/JavaScript template displays them, and navigation is a projection of the data. It does **not** authorize another database, runtime CMS, renderer, service, or public release. The backend remains the existing admitted source/edition/release records (Git, Reframe/FountainStore where relevant); production can be compiled as a source-locked immutable static edition.

## Verified defect and scope (16 November 2026, not permanent counts)

- Public `https://fountain.coach/` and `/estate/` share the same current Reader HTML digest. WebKit shows 3 horizontal published collections: Essays (10 active entries), First Readings (32 contents entries/30 illustrated entries), and Orange Dot (23 entries).
- Public `https://fountain.coach/estate/books/catalog.json` advertises all 3 with public release status. However `orderedWorkIDs` is populated only for Essays; First Readings and Orange Dot still derive order from embedded HTML/JavaScript. This is an incomplete shared catalogue projection, not permission to invent a new source database.
- Public `https://fountain.coach/estate/read/library/` returns HTTP 200 but renders an obsolete two-collection Reader with 7 Essays, 32 First Readings and no Orange Dot. The current root and this old route have different content-addressed Reader scripts. **HTTP 200 is not collection membership/parity proof.**
- Public root source retains 13 essay templates, including historical/archived works; only 10 belong to the active Essays contents. Content retention and active published membership are different facts. The deployed JS currently uses hard-coded collection arrays, excluded-work sets, template order and gallery count guards. The 16 November Better Ear blank-Reader incident confirmed that erroneous nesting of a new `<template>` can defeat startup.
- The production-collection-parity release on the same date already repaired root/direct-book/catalogue inconsistency after Better Ear; **do not reopen or undo that accepted correction**. The `/estate/read/library/` route and deterministic membership/controller refactor remain separately scoped frontend tasks, not a retrospectively completed release.

## Frontend template contract

1. **Publication model.** Read the exact admitted, ordered collection/work membership and publication states from one versioned source-bound publication snapshot. Distinguish active-public, archived-public (direct route preserved but no active listing), staged/private and unadmitted. Retain source owner, work IDs, canonical routes, media rights/provenance, stable source position and immutable revision. Treat current snapshot counts as observations, not magic constants.
2. **Projection, not authority.** Generate the public catalogue, Bookshelf contents, illustrated gallery, direct book URLs, work permalinks, metadata and accessible navigation from the *same snapshot/revision*. No second hand-maintained list in the HTML script or separate gallery selection model. An HTML embedded snapshot, pre-rendered pages and static JSON are legitimate deterministic outputs; no live database API is necessary on a publicly served static reader.
3. **HTML.** Existing source-bound Linotype document and its semantic book/collection regions remain the frontend. Keep authored work templates as top-level siblings; do not interpret a nested inert `<template>` as an admitted work. Each work is rendered only under its source work ID. Retained historical work templates do not imply active shelf membership. Preserve actual text, art, proems and audio bindings.
4. **CSS.** Maintain the established book page geometry: contents facing its gallery in eligible landscape, single-leaf/presentation switch in portrait, independent bounded vertical list/gallery scrollports and fixed footer. Horizontal discoverability must emerge visibly from neighboring *actual published collections*, using restrained typographic/page-edge treatment; avoid generic mobile-carousel ornament, overlapping controls and content cropping. Do not assume an unapproved side-tab prototype is the canonical design.
5. **JavaScript.** One collection identity and selected work drive header, complete contents, gallery, Previous/Next destinations, horizontal swipe/keyboard navigation, direct opening and restored return position. Derive adjacency and position counts from admitted published collection order; do not maintain `['essays','first-readings']` or other fixed arrays as a separate authority. Preserve source-addressed reading position on reflow/rotation and keep nested vertical scroll independent of horizontal navigation.
6. **Canonical route consistency.** Treat public `/`, `/estate/`, the supported legacy `/estate/read/library/` and each direct `/estate/books/<id>/` route as frontend projections of one currently released book inventory. Reconcile a legacy route to the current Reader or an explicit canonical redirect; never leave an HTTP-200 obsolete edition silently advertised as today's Bookshelf. Archive/deep-work routes may intentionally retain an older source edition when explicitly labelled and linked, rather than falsely claiming current membership.

## Finite acceptance for a frontend correction (not performed by this decision)

- Compute `expectedActiveBooks` and each `expectedWorkIDs` from one status-authoritative admitted edition. Compare to every supported live Bookshelf entrance, direct book route, catalogue, contents, illustrated gallery and machine/OG/JSON-LD projection. Enforce exact order, uniqueness, status, source and release identity, and first eligible source artwork. Unillustrated proems remain in contents without fabricated images; archived public works remain on their authenticated deep links but not in the current active list.
- Refuse a new source template inserted inside the `library` template, a missing published book, a stale legacy Reader module, an independently hard-coded collection count, a gallery/contents mismatch, a stale catalogue `currentReleaseID` or metadata/rights mismatch. Check that the chosen startup version creates composed pages, not merely an HTTP-200 HTML response.
- Test at desktop spread, tablet portrait and phone with the **actual** canonical template: a visible and correctly labelled horizontal continuation affordance; touch/wheel/keyboard navigation; enter/return position and selection restoration; independent vertical index scroll; unchanged original text/art/audio and direct routes. Physical iPad Safari/VoiceOver acceptance is separate from headless WebKit.
- Before declaring a release, verify the same artifact on canonical WLAN staging and separately through authorized EstatePublisher public production, with native receipts, previous-release rollback and independent HTTPS route/asset readback. This document grants **no** new production authorization.

**Current status:** Design/maintenance decision pinned only. No frontend code, active stage, public site or user-facing template was altered by this decision. Next task is a bounded source-owned frontend implementation and genuine canonical staging/browser acceptance, not another standalone review proxy or replacement publisher.
